# Agent 生成安全机制

确保 Agent 生成代码的过程安全、高效、不破坏现有功能。

---

## 1. 影响分析（修改 / 删除前必做）

修改或删除任何已有文件、export、函数前，先分析其依赖方：

```bash
# 查看谁 import 了这个文件 / export
grep -r "from.*{filename}" --include="*.ts" --include="*.tsx" -l

# 动态 import（静态 grep 容易漏）
grep -r "import(.*{filename}" --include="*.ts" --include="*.tsx" -l

# re-export 链（A re-export B，删 B 时需同时查引用 A 的位置）
grep -r "from.*{A}" --include="*.ts" --include="*.tsx" -l

# 类型引用（typeof / InstanceType 等不会在运行时报错，但类型检查会失败）
grep -r "typeof {name}\|InstanceType.*{name}" --include="*.ts" --include="*.tsx" -l
```

**修改规则：**

- 修改 `components/ui/` 下的文件 → 必须列出所有引用方，评估影响
- 修改类型定义（`types.ts`）→ 必须确认所有使用方仍然类型安全
- 修改 hooks → 必须确认所有调用方的参数和返回值仍然兼容
- 如果影响范围超出当前任务，提示用户确认后再继续

**删除规则：**

- 删除文件 → 四类引用全查（静态 import、动态 import、re-export 链、类型引用），确认全部为零再删
- 删除 export → 同上，重点检查 barrel 文件（`index.ts`）中的 re-export
- 删除 hook / 函数 → 搜索函数名在全项目的出现，含 JSX 属性和回调传参
- 引用数 > 0 时，必须在同一次改动中同步清理所有引用，或提示用户确认后再继续

## 2. 类型先行

生成新功能的顺序：

```
1. 先定义 types/interfaces
   → API 返回类型、组件 Props、状态类型

2. 再写数据逻辑
   → 数据获取 hooks、Server Actions、store（使用步骤 1 的类型）

3. 再写交互逻辑
   → 事件处理 hooks、表单逻辑（组合步骤 2 的数据方法）

4. 最后写 UI 组件
   → 渲染（使用步骤 1 的 Props 类型）
```

这个顺序确保全链路类型安全，每一层都基于已定义的类型工作。

## 3. 循环依赖防护

新增 import 时检查是否形成循环：

```
A imports B → B imports C → C imports A  ← 循环！
```

**处理方式：**

- 如果检测到循环，不要继续。提示用户并建议：
  - 提取共享类型到独立的 `types.ts`
  - 使用依赖注入或回调模式打破循环
  - 重新划分模块边界

## 4. 构建验证

**代码生成后：一轮改动完成后统一验证一次**，不要改一个文件跑一次。

**代码审查时：** 判断被审查的改动是否属于以下高风险场景，若是则执行对应验证，或在审查意见中指出"需要验证构建"。

```bash
# 类型检查（快速，默认做）
npx tsc --noEmit

# 完整构建验证（关键改动时）
npm run build
```

以下场景必须跑完整构建：

- 修改了共享类型定义
- 修改了配置文件（next.config、tsconfig）
- 大范围重构

> 注意：使用项目实际的构建命令（`npm run build` / `yarn build` / `pnpm build`），以 `package.json` 中的 scripts 为准。

## 5. 现有模式优先

生成新代码前，**先搜索项目中已有的类似实现**：

- 阅读目录结构，找到项目中同类功能的写法
- 关注 `hooks/`、`utils/`、`lib/`、`styles/` 等公共目录

**规则：**

- 有可复用的实现就用，不重复造轮子

## 6. 逻辑一致性

新增或修改功能时，必须确认**同一套业务逻辑在项目中所有出现位置保持一致**。Agent 最常犯的错误不是代码写错，而是只改了当前文件，忽略了其他页面/模块里的同类逻辑。

### 什么是逻辑一致性

同一个业务概念在不同位置的表达必须对齐，包括但不限于：

| 维度              | 示例                                                                           |
| ----------------- | ------------------------------------------------------------------------------ |
| **状态流转**      | 订单状态在列表页、详情页、筛选器中的可选值和流转路径一致                       |
| **条件分支**      | "付费用户才可见"这个判断逻辑，在导航、页面、组件中的条件表达式一致             |
| **枚举/选项顺序** | 状态筛选器的选项顺序和表格中状态列的排列逻辑一致                               |
| **分组归类**      | 设置页把"通知"归在"账户"组下，侧边栏导航也应如此，不能一处归"账户"一处归"通用" |
| **展示规则**      | 金额在列表页显示两位小数，详情页也应两位小数，不能一处 `toFixed(2)` 一处取整   |
| **业务规则**      | 新增一种计费模式时，价格展示、账单列表、用量统计页都要能处理这种模式           |

### 操作流程

新增功能或修改业务逻辑前：

```
① 识别业务概念
   "我要改的是哪个业务概念？" — 如：订单状态、用户角色、计费模式、功能权限 …

② 搜索同类逻辑
   在项目中搜索该概念的所有出现位置：
   - 搜索相关的枚举/常量名（如 OrderStatus、PLAN_TYPE）
   - 搜索相关的条件判断（如 status === 'active'、role === 'admin'）
   - 搜索 UI 上的展示位置（列表、详情、筛选器、导航 …）

③ 比对逻辑是否对齐
   - 各处的可选值是否一致？
   - 各处的条件判断是否等价？
   - 各处的排列/分组是否遵循同一规则？

④ 同步修改
   新增/修改时，所有相关位置一并更新，不遗漏
```

### 常见违反场景

- **新增枚举值只加了一处** — 常量定义里加了 `'archived'`，但筛选器、表格列映射、状态流转图没同步
- **条件逻辑不一致** — 页面 A 用 `user.plan !== 'free'` 判断付费用户，页面 B 用 `user.isPro`，两者语义未必等价
- **展示逻辑局部遗漏** — 新增了一种卡片类型，列表页能渲染，但详情页 switch 分支没覆盖，走了 default 或报错

## 7. 作用域边界

Agent 修改文件前，根据风险等级决定是否需要用户确认：

**🟢 低风险 — 直接修改：**

- 当前任务直接涉及的业务页面和组件
- 当前功能模块内部的 types、hooks、utils（仅该模块使用）
- 新建文件

**🟡 中风险 — 谨慎修改，必要时询问用户：**

- `components/ui/` 下的共享 UI 组件（被多处引用）
- `app/` 下跨模块共享的 `hooks/`、`lib/`、`utils/`（改动可能影响其他功能）
- package.json（添加/删除依赖）
- 全局配置文件（next.config、tsconfig、eslint config）
- 其他团队成员正在开发的模块

> 判断依据：修改是否会影响当前任务之外的代码。如果只改接口不改行为，可以直接做；如果改了签名、删了导出、或改了默认行为，先和用户确认。

**🔴 高风险 — 仅在用户明确指令下修改：**

- `.env` / `.env.local`（含敏感信息）
- lock 文件（只通过包管理器命令间接修改）
- `node_modules/`
- `scripts/`（构建/部署脚本等基础设施，改动可能破坏流程）
- 构建生成目录（如 `src/dictionaries/` 等，会被脚本覆盖）

## 8. 回滚安全

- 大范围改动前，建议用户先 commit 当前状态
- 删除代码时谨慎：确认没有其他地方引用
- 不在同一次改动中做"功能开发 + 重构"——分开做

## 9. 业务安全

生成代码时必须识别并防范敏感信息泄露风险：

**禁止出现在前端代码中的内容：**

- API Key、Secret Key、Token 等凭证（包括作为默认值、placeholder、fallback）
- 数据库连接字符串、内部服务地址
- 用户隐私字段的明文展示（手机号、身份证、邮箱等未脱敏）

**常见风险场景：**

- 参数默认值写了真实 key：`const apiKey = props.apiKey ?? "sk-xxxx"`
- 环境变量缺少 `NEXT_PUBLIC_` 前缀判断，服务端变量意外暴露到客户端
- 错误信息中包含内部路径、堆栈、或数据库结构
- 业务代码中残留 mock 数据（硬编码假数据、import `mock/` 目录文件、`MOCK_` 前缀变量），详见 [`mock-rules.md`](./mock-rules.md)

**规则：**

- 凭证类值只能从环境变量读取，不硬编码
- 客户端组件（`'use client'`）中不允许访问非 `NEXT_PUBLIC_` 环境变量
- 用户隐私字段展示时使用脱敏处理（如 `138****1234`）

生成完成后的结果检查，见 [`checklist.md`](./checklist.md)。
