# 代码生成工作流

以 Agent 视角定义：**当前该做什么操作、有什么约束。**

基于用户意图驱动执行，每个意图有完整的步骤和检查点。

---

## 【新建（Create）】— 新功能 / 多文件 / Figma 还原

> 📍 **进入时声明：**「当前意图：新建 → 完成后进入：验证」

**触发：** 新建功能模块、多组件联动、涉及数据流变更、还原 Figma 设计稿

### Step 0: 分析（动手前必做）

分析目标是：**清楚知道要做什么、改哪里、涉及哪些领域。**

以下情况可**快速分析**（只确认目标文件和作用域，跳过全量领域分析）：
- 指令已足够明确（如"实现 X 组件，效果如 Y"）
- 明确的功能描述，边界清楚

信息缺失或有歧义时，简要确认：
- **预期效果** — 最终要实现什么？有设计稿或参考吗？
- **涉及范围** — 哪些页面/组件？哪些明确不动？
- **数据来源** — API 已有还是需要 mock？
- **约束条件** — 兼容性、性能、无障碍等特殊要求

按任务内容识别涉及领域，只分析涉及部分：

| 领域 | 识别要点 | 代码分析动作 |
|------|---------|-------------|
| **需求范围** | 涉及哪些页面/模块？边界在哪？哪些明确不动？ | 确认目标文件和影响面，搜索已有类似实现 |
| **UI 视觉** | 有无设计稿（Figma）？需要还原哪些视觉细节？ | 读现有页面的样式模式、确认 token 用法 |
| **数据流** | 数据从哪来（API / store / props / URL）？ | 追踪数据从 API → hook/store → 组件的完整路径 |
| **交互逻辑** | 用户操作路径？触发什么事件？状态怎么变？ | 读现有事件处理模式，确认状态管理方式 |
| **业务规则** | 涉及哪些条件判断（权限、状态、角色）？ | 搜索同一业务概念在项目中的所有出现位置 |
| **异常兜底** | 空状态 / 加载态 / 错误态 / 数据边界 / 权限异常 | 确认项目已有的兜底模式 |
| **路由 / 导航** | 是否新增页面？URL 结构？导航菜单需同步？ | 确认路由结构和导航配置位置 |
| **类型定义** | 需要新增或修改哪些类型？影响哪些上下游？ | 确认已有类型，判断是扩展还是新建 |

如有 preview 文件，阅读理解目标效果。确认 RSC 边界划分。

### Step 1: 类型定义

```
├── Props 类型、API 响应类型、状态类型
└── 复用已有定义，保持一致
```

### Step 2: 数据逻辑

```
├── Server Actions / 数据获取 hooks / store
├── 接入真实 API（或替换已有 mock）
└── 错误处理
```

### Step 3: 交互逻辑

```
├── 事件处理 hooks
├── 表单逻辑
└── 流程编排
```

### Step 4: UI 组件

```
├── 组件渲染
├── 加载/错误/空状态处理
├── 响应式布局
└── 样式（严格使用 system token）
```

### Step 5: 清理

```
├── 删除不再需要的 preview 文件和对应 mock
├── 确认无 mock import 残留在业务代码
└── 路由注册、导航更新（如需要）
```

**约束：**
- 代码按职责归位（`code-layering.md`）
- 配置变更与业务变更分开处理（`change-scope-control.md`）
- 修改共享代码前做影响分析（`agent-safety.md`）

**✅ 新建完成 →** 进入【验证】

## 【修改（Modify）】— 小改动 / 样式 / 数据源替换

> 📍 **进入时声明：**「当前意图：修改 → 完成后进入：验证」

**触发：** 单组件修改、样式调整、文案变更、替换 mock 为真实 API、简单交互改动

### Step 0: 分析（确认范围）

以下情况**跳过**，直接进入 Step 1：
- 指令已足够明确（如"把按钮颜色改成 primary"）
- 同一任务的后续轮次（上下文已建立）
- 明确的 bug 修复（现象和预期都清楚）

其他情况确认：
- **目标文件** — 改哪个文件/组件/样式？
- **作用域** — 只改这里，不动其他

> **规模升级：** 发现需要新建模块、多文件联动、数据流变更 → 转为**新建**意图。

### Step 1: 直接修改

```
├── 在正式代码中修改
├── 样式使用 system token
├── 替换数据源时确认类型一致
└── 遵循已有代码模式
```

### Step 2: 清理

```
├── 删除被替换的 mock（如有）
└── 确认无残留引用
```

**约束：**
- 改动范围必须可控，超出预期则升级为新建
- 替换数据源后确认类型端到端一致（API 响应 → 组件 Props）

**✅ 修改完成 →** 进入【验证】

## 【原型（Prototype）】— 隔离验证，不碰正式代码

> 📍 **进入时声明：**「当前意图：原型 → 完成后用户确认方案，再进入：新建」

**触发：** "先看下效果"、"做个演示"、"试试方案"

**行为：**
1. 创建 `*.preview.tsx`，加 `// @generated-preview` 标记
2. 所有视图代码写在 preview 文件中，不修改已有业务文件
3. 数据使用 `mock/` 目录的 mock 文件，不硬编码
4. 可以 import 项目已有的共享组件
5. 样式仍须遵循 system token 规则
6. 不需要处理错误/加载/边界状态（原型关注主流程）

**✅ 原型完成 →** 展示给用户确认方案，待确认后转为**新建**意图正式实现

---

## 【验证（Verify）】— 每轮改动后

> 📍 **进入时声明：**「当前意图：验证 → 通过后本轮完成 / 发现问题则返回对应意图修复」

一轮改动完成后统一验证，不逐文件触发。

### Step 1: 代码检查

```
├── 对修改文件执行 lint:fix + format
├── tsc --noEmit 类型检查
└── 确认无循环依赖
```

### Step 2: 自检

```
├── 运行生成后自检清单（checklist.md）
├── 确认无 preview/mock 残留在业务代码
└── 确认业务安全（无硬编码凭证、无敏感信息泄露）
```

### Step 3: 构建（关键改动时）

以下情况执行 `npm run build` 完整构建验证：
- 修改了共享类型定义
- 修改了配置文件
- 大范围重构

**✅ 验证通过 →** 本轮任务完成；**⚠️ 发现问题 →** 声明返回对应意图（新建 / 修改）修复，修复后重新进入【验证】

## 共性规则

无论哪种意图，始终适用：

1. **样式使用 system token** — 不硬编码色值/间距
2. **代码分层** — 各类代码按职责归位，不混放
3. **现有模式优先** — 先找项目已有实现，复用而非重造
4. **类型安全** — 所有数据流都有类型定义
5. **影响分析** — 修改共享代码前评估影响范围
